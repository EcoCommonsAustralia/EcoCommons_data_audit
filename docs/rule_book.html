Rule Book

Rule Book

Contact details: support@ecocommons.org.au

Date: September 2026

Purpose

The metadata rules and data standards that EcoCommons datasets are expected to satisfy — each rule stated, justified, and made checkable, with pass/fail examples.

This page is the living rule book for EcoCommons data. It turns loose expectations — “titles should be consistent”, “every dataset needs a category” — into explicit, checkable rules, so that a dataset can be audited against them objectively rather than by opinion.

Each rule ties back to the metadata fields exposed by the data-ingester index (the same fields we pulled in the production catalogue audit):

title · uuid · data_category · data_subcategories · time_domain · year · resolution · spatial_domain · spatial_data_type · collection_names · downloadable · created

Note

This is a proposed rule set, grounded in the production catalogue audit of all 58,424 records. Obligations, controlled vocabularies, and the Current status figures are offered for EcoCommons / Biosecurity Commons review — confirm and ratify them before any rule is enforced.

How to read a rule

Every rule follows the same template so it can be applied and, eventually, automated:

Field Meaning
Rule ID Stable identifier (e.g. MD-001).
Statement The rule itself, phrased as a requirement (“must”, “should”).
DCAT-AP Obligation + cardinality + the DCAT / DCAT-AP property it maps onto (see Alignment with DCAT-AP).
Applies to Which datasets / fields the rule governs.
Rationale Why the rule exists (FAIR, discoverability, interoperability…).
Check How to test compliance — a concrete condition.
✅ Pass / ❌ Fail An example that satisfies the rule and one that violates it.

We adopt the DCAT-AP obligation model, so severity maps directly onto an accepted standard: MUST ↔︎ Mandatory (M), SHOULD ↔︎ Recommended (R), MAY ↔︎ Optional (O). A property is Mandatory exactly when its minimum cardinality is ≥ 1 (cardinality is written min..max, e.g. 1..1, 1..*, 0..1).

Alignment with DCAT-AP

DCAT-AP 3.0 describes each dataset property with an obligation (Mandatory / Recommended / Optional) and a cardinality (min..max). We map the EcoCommons index fields onto DCAT / DCAT-AP properties so these rules inherit an accepted standard rather than inventing one. Geospatial specifics (resolution) follow GeoDCAT-AP; two fields have no DCAT equivalent and are flagged as EcoCommons extensions.

EcoCommons field DCAT / DCAT-AP property DCAT-AP obligation Card. Notes
title dct:title Mandatory 1..* —
description dct:description Mandatory 1..* Enforced by MD-004
data_category dcat:theme Recommended 0..* Bind to an EcoCommons theme vocabulary (local codelist)
data_subcategories dcat:keyword Optional 0..* —
time_domain dct:temporal Optional 0..* Current / Future / Historical is an EcoCommons extension of temporal coverage
year dct:temporal Optional 0..1 —
spatial_domain dct:spatial Optional 0..* Bind to a places codelist (e.g. Countries NAL)
resolution geodcat:spatialResolution Optional 0..1 GeoDCAT-AP
spatial_data_type (none) — — EcoCommons extension (Continuous / Categorical)
collection_names dcat:DatasetSeries / catalogue membership — 0..* —
uuid dct:identifier Optional 0..* —
created dct:issued (+ dct:modified) Optional 0..1 —
downloadable dcat:Distribution / dct:accessRights Optional 0..1 Access handled at distribution level
Tip

Where a rule is stricter than DCAT-AP — e.g. we make category MUST/mandatory though DCAT-AP only recommends dcat:theme — that is an intentional EcoCommons tightening, and it is noted on the rule.

1. Metadata rules

MD-001 — Every dataset MUST have a category

Statement. Every dataset must populate data_category with a value from the controlled vocabulary.

DCAT-AP. Obligation MUST (stricter than DCAT-AP, which only recommends dcat:theme) · cardinality 1..* · aligns to dcat:theme.

Applies to. All datasets.

Rationale. Category drives filtering and discovery in the data explorer; an uncategorised dataset is effectively invisible to users browsing by theme.

Controlled vocabulary. Climate, Vegetation, Biodiversity, Marine, Topography, Human Activity, Freshwater, Soil, Boundary Data — the nine categories observed across the production catalogue.

Check. A dataset fails if its category is missing, empty, “Unknown”, or outside the vocabulary.

Current status. 45 of 58,424 records (≈0.08%) are uncategorised/unknown and fail this rule; the remaining 58,379 carry one of the nine values.

✅ Pass — data_category: "Climate"
❌ Fail — data_category: "" or data_category: "Unknown"

MD-002 — Time domain MUST be a controlled value

Statement. time_domain must be exactly one of Current, Future, or Historical.

DCAT-AP. Obligation MUST · cardinality 1..1 · aligns to dct:temporal (EcoCommons classification extension).

Rationale. Temporal scope is a primary filter for model inputs; free-text or missing values break the “current vs future climate” split.

Check. time_domain ∉ {Current, Future, Historical} → fail.

Current status. All 58,424 records carry a value — Future (54,614) or Current (3,810); none are missing. Historical is defined in the vocabulary but is currently unused in production.

✅ Pass — time_domain: "Future"
❌ Fail — time_domain: "2050" or empty.

MD-003 — Future datasets SHOULD declare scenario and model

Statement. When time_domain = "Future", the dataset should record its emissions scenario and climate model (e.g. emsc/gcm, or embedded in the title).

DCAT-AP. Obligation SHOULD · cardinality 0..1 · relates to dct:temporal and dct:title.

Rationale. A future-climate layer is not interpretable without knowing the GCM and SSP/RCP it came from.

✅ Pass — title "… (2021-2040), HADGEM3-GC31-LL ssp245, 10 arcmin (~20km)"
❌ Fail — title "Future minimum temperature August" (no model, no scenario).

MD-004 — Every dataset MUST have a description

Statement. Every dataset must populate description with a non-empty, human-readable summary of what the layer is.

DCAT-AP. Obligation MUST · cardinality 1..* · aligns to dct:description (Mandatory in DCAT-AP).

Applies to. All datasets.

Rationale. A title alone rarely conveys provenance, units, or intended use; the description is the primary free-text field search and users rely on. FAIR Findable / Reusable.

Check. A dataset fails if description is missing, empty, or merely repeats the title verbatim.

✅ Pass — description: "WorldClim v2.1 downscaled future minimum temperature for August, 2021-2040, GCM HADGEM3-GC31-LL under SSP2-4.5…"
❌ Fail — description: ""

MD-005 — Every dataset MUST have a unique identifier

Statement. Every dataset must carry a uuid that is present and unique across the catalogue.

DCAT-AP. Obligation MUST (stricter than DCAT-AP, which makes dct:identifier Optional) · cardinality 1..1 · aligns to dct:identifier.

Applies to. All datasets.

Rationale. The uuid is the stable key for every per-record API call (GET /api/dataset/{uuid}) and is the only field reliable enough to sort/paginate the index on — _id and uuid.keyword are not. A missing or duplicate uuid makes a dataset unaddressable and breaks enumeration.

Check. uuid empty, or any uuid value appearing on more than one record → fail.

Current status. All 58,424 records sorted and paged cleanly on uuid during the audit — no gaps or collisions observed.

✅ Pass — uuid: "a3f1c2e4-…" (unique)
❌ Fail — uuid: "", or two records sharing one uuid.

MD-006 — Datasets SHOULD record an issued date

Statement. Each dataset should record when it was added to the catalogue via created.

DCAT-AP. Obligation SHOULD · cardinality 0..1 · aligns to dct:issued (and dct:modified on change).

Applies to. All datasets.

Rationale. An issued date lets users and auditors reason about freshness and change over time, and underpins “what’s new since…” views.

Check. created missing or unparseable as a date → fail (SHOULD, so advisory).

✅ Pass — created: "2024-11-03T09:12:00Z"
❌ Fail — created: ""

2. Naming & title standards

NM-001 — Titles SHOULD follow the canonical pattern

Statement. Dataset titles should follow the canonical pattern: Source/Product, variable (period), model/scenario, resolution.

DCAT-AP. Obligation SHOULD · aligns to dct:title (which DCAT-AP makes Mandatory, 1..* — presence is assumed; this rule governs its form).

Rationale. A predictable title structure makes long lists scannable and sortable, and lets users compare like-for-like layers across products.

✅ Pass — "WorldClim v2.1, future climate Minimum Temperature August (2021-2040), HADGEM3-GC31-LL ssp245, 10 arcmin (~20km)"
❌ Fail — "min temp aug worldclim"

NM-002 — Resolution MUST use the standard notation

Statement. resolution must be expressed as <value> <unit> (~<approx>), e.g. 10 arcmin (~20km), 30 arcsec (~1km).

DCAT-AP. Obligation MUST · cardinality 0..1 · aligns to geodcat:spatialResolution (GeoDCAT-AP).

Rationale. Consistent resolution strings let users match datasets to a target grid and are machine-parseable.

✅ Pass — "30 arcsec (~1km)"
❌ Fail — "1km", "0.0083 deg", empty.

3. Data standards

DS-001 — Spatial data type MUST be declared

Statement. spatial_data_type must be one of Continuous or Categorical.

DCAT-AP. Obligation MUST · cardinality 1..1 · EcoCommons extension (no DCAT-AP equivalent).

Rationale. Downstream models treat continuous and categorical predictors differently; misclassification silently corrupts results.

✅ Pass — spatial_data_type: "Continuous"
❌ Fail — missing, or a numeric/other value.

DS-002 — Every dataset MUST belong to a collection

Statement. collection_names must be non-empty.

DCAT-AP. Obligation MUST · cardinality 0..* · aligns to dcat:DatasetSeries / catalogue membership.

Rationale. Collections are how related layers are grouped for users; orphan datasets (None) are hard to find and to govern.

Check. collection_names empty or ["None"] → fail.

Current status. Production holds ~54 collections; the catalogue is heavily skewed — WorldClim-v2.1 alone accounts for 52,308 records (≈90%), so most datasets are well-placed, but orphan checks matter for the long tail.

✅ Pass — collection_names: ["WorldClim-v2.1"]
❌ Fail — collection_names: []

DS-003 — Spatial domain SHOULD be declared

Statement. spatial_domain should be populated from a places codelist (e.g. Australia, Global, a state/territory).

DCAT-AP. Obligation SHOULD · cardinality 0..* · aligns to dct:spatial.

Applies to. All datasets.

Rationale. Geographic extent is a primary discovery filter; a layer with no declared spatial domain cannot be found by “data for Australia” queries and risks being applied outside its valid footprint.

Check. spatial_domain empty, or a value outside the agreed places codelist → fail (advisory).

✅ Pass — spatial_domain: "Australia"
❌ Fail — spatial_domain: ""

DS-004 — Access MUST be declared explicitly

Statement. downloadable must be an explicit boolean (true / false), never absent or blank.

DCAT-AP. Obligation MUST · cardinality 1..1 · aligns to dcat:Distribution / dct:accessRights (declared at the dataset level here).

Applies to. All datasets.

Rationale. Users and tooling need to know up front whether a layer can be exported; an undefined access flag forces a trial-and-error download attempt and breaks automated harvesting.

Check. downloadable missing or non-boolean → fail.

✅ Pass — downloadable: true
❌ Fail — downloadable: null or absent.

References & prior art

This rule book is deliberately lightweight, but it follows the same pattern as established metadata and data-quality standards: each field carries an obligation level (mandatory / recommended / optional) and is often bound to a controlled vocabulary (codelist). The standards below are the best templates to align with — and, over time, to borrow controlled vocabularies from.

Geospatial metadata & quality standards

  • ISO 19115-1 (geographic metadata) and ISO 19157 (data quality) — the mainstream geospatial standard. Elements carry Mandatory / Conditional / Optional obligations (the analogue of our MUST / SHOULD / MAY) and bind to codelists. Normative text is paywalled by ISO; open overviews: DCC guide · ICA wiki.
  • FGDC CSDGM — the long-standing US Content Standard for Digital Geospatial Metadata, same obligation model: fgdc.gov/metadata/csdgm-standard.
  • INSPIRE metadata (EU) — ships an official online validator that reports pass/fail against the rules; the automatable end-state of our Check field: inspire.ec.europa.eu/validator.

Catalogue / FAIR profiles (closest to this Rule Book’s format)

  • DCAT-AP — a W3C DCAT application profile defining per-field cardinalities and obligations plus recommended controlled vocabularies. The closest structural match to this page (see Alignment with DCAT-AP above): DCAT-AP 3.0 spec · W3C DCAT.
  • GeoDCAT-AP — the geospatial extension of DCAT-AP (adds spatial resolution, reference system, etc.), the source for our resolution mapping: GeoDCAT-AP.
  • FAIR principles — the guiding rationale (Findable, Accessible, Interoperable, Reusable): go-fair.org/fair-principles.

Ecology / biodiversity domain standards (relevant to EcoCommons)

  • Darwin Core — biodiversity occurrence data terms: dwc.tdwg.org.
  • EML — Ecological Metadata Language — dataset metadata for ecology: eml.ecoinformatics.org.

Making rules machine-checkable

  • SHACL — validate RDF / DCAT metadata against constraint “shapes”: w3.org/TR/shacl.
  • Frictionless Data (Table Schema) — declarative field/row validation for tabular data: frictionlessdata.io.

If you have questions or suggestions, please contact the EcoCommons team.
